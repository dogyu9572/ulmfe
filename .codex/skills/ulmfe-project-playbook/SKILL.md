# ULMFE Project Playbook

## 기준 문서

작업 전에 필요한 범위만 읽되, 기능 맥락이 흔들리면 아래 3개 기획서를 함께 대조한다.

- 관리자 페이지 기획: `docs/개발 기획서/울산광역시미래교육관_관리자_화면설계서_ver1_0_HK20260611.pptx`
- 사용자 웹페이지 기획: `docs/개발 기획서/울산미래교육관_누리집 사용자 기획_v.1.0_260529.pdf`
- 사용자 패드용 앱 기획: `docs/개발 기획서/울산미래교육관_학습지원시스템_v1.0_260529.pdf`

나중에 작성해야 할 산출물 양식은 `docs/작성 양식`을 기준으로 참고한다. 이 폴더의 기존 내용은 다른 프로젝트 자료이므로 요구사항 근거로 사용하지 말고, 문서 형식과 채워야 할 항목만 참고한다.

보조 자료는 `docs/(작성 중)산출물 정리`의 기존 양식과 완성 예시를 참고한다. 전체를 무조건 읽지 말고, 산출물 종류가 맞는 파일만 확인한다.

## 개발 순서

1. 전체 구조는 하나의 서버와 공통 DB를 전제로 이해한다.
2. 구현은 관리자 페이지를 먼저 진행한다.
3. 사용자 웹페이지는 관리자 기능과 데이터 구조가 안정된 뒤 진행한다.
4. 사용자 패드용 앱은 하이브리드/네이티브가 확정되지 않았으므로, 앱 기술 결정이 필요한 변경은 설계 대안과 영향 범위를 먼저 정리한다.
5. 한 번에 여러 메뉴를 밀어붙이지 말고, 메뉴 또는 화면 단위로 계획 -> 구현 -> 검증 -> 사용자 검수 순서로 진행한다.
6. 자동 재시작이 켜진 개발 환경을 전제로, Codex는 먼저 읽기/분석/계획을 끝낸 뒤 파일 저장을 마지막에 최대한 한 번으로 묶는다. 중간 저장이 필요하면 저장 전에 사용자에게 알린다.

## 관리자 개발 우선순위

관리자 개발은 온전한 신규 개발보다 전체 메뉴 골격과 기존 기본 모듈 재활용을 먼저 정리한다.

1. 관리자 메뉴 구성을 먼저 완료한다. 메뉴 구성이 되어야 전체 범위와 진척률이 정리된다.
2. 현재 연결 가능한 기본 모듈이 있으면 실제 라우트로 연결한다.
3. 아직 모듈이 없는 메뉴는 빈값 또는 예상 가능한 URL로 라우팅 값을 잡아 메뉴 자리를 먼저 만든다.
4. 만들어져 있는 기본 모듈은 기획서의 메뉴명·화면명과 최대한 동일하게 명칭을 맞춰 배치한다.
5. 기획서와 얼추 맞도록 필요한 범위만 커스터마이징한다. 핵심 기능이 이미 동작하면 세부 UI/부가 요구는 스킵하거나 후순위로 둔다.
6. 기본 모듈 재활용이 어려운 메뉴를 신규 개발한다. 신규 개발 우선 후보는 교육프로그램관리, 학습관리, 도서관리다.

## 메뉴 단위 작업 흐름

각 메뉴나 화면을 시작할 때 다음을 먼저 정리한다.

- 기획서 출처: 문서명, 슬라이드/페이지, 화면명
- 사용자 유형: 관리자, 사용자 웹, 패드 학생용, 패드 선생님용
- 데이터 흐름: 화면 입력/출력, API, Service, DAO/Mapper, DB 테이블
- 산출물 영향: 요구사항정의서, 메뉴구성도, 프로그램정의서, 테이블정의서, 인터페이스정의서, 테스트 시나리오
- 검수 기준: 사용자가 직접 확인할 화면 흐름과 성공/실패 조건

사용자에게 검수받기 전에는 다음 메뉴로 넘어가지 않는다.

## 관리자 UI 반영 기준

관리자 개발에서는 현재 프로젝트에 이미 있는 기본 관리자 모듈의 디자인, 레이아웃, 버튼 위치, 테이블 구조, 검색 영역, 등록/수정 폼 패턴, 공통 컴포넌트, CSS를 우선 유지한다.

- 기획서에서 반드시 반영할 것: 메뉴명, 화면명, 관리 항목, 필드, 설명/디스크립션, 안내 문구, 상태값, 버튼 기능, 데이터 흐름, 검수 조건
- 기획서에서 그대로 따라 하지 않을 것: 시안의 색상, 여백, 버튼 배치, 컴포넌트 모양, 표/폼의 시각적 레이아웃, 장식적 디자인
- 기획서와 기존 관리자 UI 패턴이 충돌하면 기존 관리자 UI 패턴을 우선하고, 누락되면 가장 유사한 기존 화면의 패턴을 따른다.
- 버튼 위치나 화면 구성 변경이 기능 이해에 꼭 필요하다고 판단되면 먼저 이유와 영향 범위를 설명하고 사용자 확인을 받는다.
- 관리자 화면 작업 전에는 가장 비슷한 기존 관리자 화면을 찾아 "UI 기준 화면"으로 삼는다.

## 공공기관 산출물 기준

DB나 API를 추가/수정하면 산출물 갱신 대상을 함께 언급한다.

- DB 테이블/컬럼: 테이블목록및정의서, DB표준사전, ERD, 데이터표준관리방안
- API/연계: 인터페이스정의서
- 화면/프로그램: 요구사항정의서, 요구사항추적표, 메뉴구성도(IA), 프로그램정의서
- 검증: 단위테스트 시나리오, 통합시험 시나리오, 웹접근성/웹호환성 점검 자료

산출물 작성 또는 개발 계획 수립 시 `docs/작성 양식`에서 해당 문서 양식을 먼저 확인한다. 양식 안의 기존 프로젝트명, 화면명, 테이블명, 수치, 일정, 담당자, 시스템명은 ULMFE 요구사항으로 간주하지 않는다.

컬럼명, 코드명, 용어는 먼저 `src/행정안전부_공공데이터공통표준용어.csv`와 기존 DB/VO/Mapper 관례를 대조한다. 표준 용어와 기존 프로젝트 관례가 충돌하면 임의로 결정하지 말고 후보와 근거를 제시한다.

## 설계 주의사항

- 같은 DB를 공유하므로 관리자 데이터 구조가 사용자 웹/패드앱 요구사항을 막지 않는지 확인한다.
- 관리자 CRUD는 이후 사용자 화면 노출, 예약, 학습결과, 통계, 콘텐츠 관리까지 이어질 수 있게 식별자와 상태값을 안정적으로 설계한다.
- DB 스키마 변경, 실제 데이터 변경, 권한/인증/공통 설정 변경은 사용자 확인 후 진행한다.
- 사용자가 DB 조회/반영을 지시했거나 이미 확인한 DB 작업은 샌드박스 TCP 소켓 제한으로 인한 불필요한 재시도를 피하기 위해 처음부터 승인 실행(`require_escalated`)으로 수행한다.
- 사용자 앱은 기술 방식이 미정이므로 앱 전용 기능을 서버 계약(API, 인증, 파일, 오프라인 가능성, 태블릿 관리번호 등)과 분리해서 기록한다.
- 기획서와 현재 코드가 다르면 기획서 요구, 현재 구현, 제안 변경을 나눠서 보고한다.
- 계속 지켜야 할 개발 행동 규칙은 AGENTS.md 또는 skill에 기록하고, 의사결정 기록·분석 요약·개발 계획처럼 참고용 성격이 강한 내용은 `docs/*.md`에 별도 문서로 정리한다.
